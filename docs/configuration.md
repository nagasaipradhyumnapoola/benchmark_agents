# Configuration

Default storage is `.bench-agents/bench-agents.sqlite3` plus local `artifacts/` and isolated `workspaces/`. Set `BENCH_AGENTS_DATA_DIR` in API, worker and CLI consistently. New workspaces start with empty model, agent and experiment inventories; built-in task definitions remain available. Demonstration inventory is installed only by an explicit demo action. The project does not require a database account. PostgreSQL/object-store deployments are not included in the tested default and must be provided by an explicit extension.

The Python package namespace remains `benchlab` for import compatibility. The old `benchlab` command and `BENCHLAB_*` environment names remain supported; a present `BENCH_AGENTS_*` value takes precedence. Existing `.benchlab` directories are not automatically migrated or deleted. To retain an older workspace, back it up and migrate deliberately before using the new default; the current live workspace contains no old demonstration records.

Provider credentials live in environment variables. A model configuration stores `api_key_env`, the **name** of one variable, never its value. URLs reject embedded userinfo, query and fragment secrets. Config JSON rejects unknown fields. CLI `models add` and `agents add` accept JSON or TOML files; the web forms expose common fields and validated advanced JSON overrides.

Model configuration: id/name, adapter, model ID, credential-free base_url, optional api_key_env, declared capabilities, known context window, optional input/output prices per million tokens, demo flag and description. Capabilities are declarations; discovery probes do not magically verify them.

Agent configuration: id/name, adapter, executable, argv array, optional model_flag, capability declarations, env_allowlist, native/demo flags. A controlled generic subprocess harness must explicitly bind the selected model name and endpoint using model_flag and model_base_url_env; credentialed binding also requires model_api_key_env. Those fields contain variable names. Native Codex/OpenCode interfaces are full-product comparisons; their endpoint/auth profiles are owned by the native product, so unsupported controlled model binding is rejected.

Native execution requires BOTH `BENCH_AGENTS_ALLOW_HOST_PROCESS=1` in the backend and `allow_host_process=true` in the experiment. It is a privileged host process, not a filesystem/network sandbox. Use an isolated OS account or VM. Environment inheritance is restricted and auth profiles are not silently reused. Bench Agents never executes arbitrary shell strings from HTTP.

Native host agents must explicitly select `isolation: workspace`; Docker isolation claims are rejected for those adapters. Windows environment filtering preserves OS runtime variables case-insensitively. Known Codex/OpenCode npm shims resolve to Node/native entry points without a shell; generic cmd/bat/PowerShell launchers must instead be configured as an interpreter plus explicit script args. `workspace_provider: builtin` is the default; trusted registered preparation/cleanup extensions may select another name without changing the sandbox policy.

Experiment configuration includes name/description/mode, explicit systems, benchmark/task IDs, trials (1–50), total wall-clock budget, per-task timeout, max output tokens, optional observed-usage token/cost caps, retries/backoff, memory/CPU limits for applicable environments, isolation, host consent, network/tools, verifier policy, tags, baseline and seed. Empty starter task selection means the eight default text tasks. Coding and workspace tasks require explicit selection and capabilities. Generated code never falls back to host execution.

The server uses loopback port 8000; web port 3000 proxies `/api`. `BENCH_AGENTS_API_URL` sets the web server's backend origin at build/start configuration. `BENCH_AGENTS_WEB_ORIGIN` adds one explicitly trusted browser origin to API protections. Do not add wildcard origins or expose the service publicly without authentication and an appropriate threat model.
